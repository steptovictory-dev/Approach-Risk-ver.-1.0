# Контракт внешних данных

Корень данных задается через `SAMPLE_SELECTION_DATA_ROOT`. Структура путей сохраняется для явного происхождения артефактов. Полные массивы не копируются в исследование. Нужны следующие Parquet:

| Путь внутри корня | Назначение |
| --- | --- |
| `europe/data/source/osn23_landings_merged.parquet.gzip` | Исходная популяция |
| `europe/data/working/04_c40_ambiguous_pairs_excluded.parquet` | После исключения пар |
| `europe/data/analytical/04_c40_available.parquet` | После условий C40 |
| `europe/data/analytical/06_05_cases_excluded.parquet` | Финальная популяция |
| `europe/data/review/04_05_c40_pair_full_records.parquet` | 294 исключенные записи пар |
| `europe/data/review/06_02_lsgg_excluded_record.parquet` | Один согласованный случай |
| `europe/data/review/06_04_cfl12_excluded_record.parquet` | Один согласованный случай |
| `europe/data/review/06_04_excluded_profile_records.parquet` | Четыре согласованных случая |
| `europe/data/review/06_05_excluded_records.parquet` | Три согласованных случая |

JSON-журналы из `europe/reports/` перечислены в ячейке происхождения ноутбука. Их список намеренно явный: отсутствующий журнал останавливает выполнение. Полный массив без входов не воспроизводится из одних итоговых CSV.

## Поля, используемые в эксперименте

| Поле | Смысл и роль |
| --- | --- |
| `flight_id` | Идентификатор источника; часть ключа, не уникальный самостоятельно |
| `icao24` | Адрес борта; часть ключа |
| `airport` | Аэропорт события; ключ и группировка |
| `landing_time` | Время события UTC; ключ, календарные год и месяц аудита |
| `GoA` | Булева исходная метка; null останавливает расчет |
| `attempt_times` | Список времен попыток; первый элемент задает временной критерий |
| `C40_CROSS_TIME` | Время точки C40; полнота, согласованность и проверка сохранности |
| `C40_BEARING` | Числовое поле направления C40; проверка заполненности и конечности |
| `C40_CROSS_LAT`, `C40_CROSS_LON` | Координаты C40; проверка заполненности и конечности |
| `typecode` | Исходный код типа; группировка без справочного подменивания |
| `market_segment` | Исходный сегмент; группировка, пропуск отдельной категорией |

Смысл C40 принимается из постановки исходного проекта; геометрия и соответствие точки нужному событию здесь не доказываются. Порядок первого элемента `attempt_times` был проверен прежним аудитом, но текущий ноутбук не реконструирует траектории. Неполные ключи и пустые списки попыток останавливают выполнение.

## Выходные показатели

`rows` – число записей; `goa` – число меток True. `goa_pct` имеет знаменатель `rows` соответствующей группы и этапа. `retained_pct` сравнивает объем с исходным объемом; показатели сохранения по меткам используют исходное число соответствующей метки. `composition_pct` – вес группы в полном объеме этапа. `delta_goa_pp` и `composition_delta_pp` выражены в процентных пунктах. `outside` – разность источника и финала. При нулевом знаменателе доля остается NaN.

В `rule_overlap.csv` поле `not_before` означает отсутствие подтвержденного строгого отношения C40 < первая попытка, включая пропущенное время. Это не отдельная исключающая причина; взаимоисключающие причины находятся в `exclusive_reasons.csv`.

Третий ноутбук добавляет `type_missing` – булев признак null или точной пустой строки исходного typecode. `c40_missing_pattern` кодирует пропуски битами: время 8, направление 4, широта 2, долгота 1; 0 означает отсутствие физических пропусков, 15 – отсутствие всех четырех полей. Конечность чисел и временные условия проверяются отдельно.

В разложении `w0`, `w1` – веса группы в источнике и финале, `p0`, `p1` – доли GoA в диапазоне 0–1. `composition_pp` использует исходные доли как опору; `within_pp` – изменение внутри группы с финальным весом. `absent_group_support_pp` сравнивает весь источник с его подмножеством в группах, представленных в финале; `common_support_delta_pp` – оставшаяся разница. Эти компоненты арифметические, не причинные. Для исчезнувшей группы `p1` остается NaN; внутри формулы ее нулевой финальный вес дает нулевой внутренний вклад.

Стандартизация type_missing использует общие исходные веса аэропорта × месяца только в стратах с обеими группами типа. Нулевое финальное сохранение остается нулем. Стандартизация не задает веса для обучения модели. Совместный финальный разрез независимо проверяется чтением итогового файла; полный массив ключей повторно не сопоставляется, поскольку эта проверка выполнена первым ноутбуком.

## Эксперимент B

Четвертый ноутбук читает только финальный parquet с тем же SHA256, что в проверке A.
Для отдельного репозитория предусмотрен путь `data/06_05_cases_excluded.parquet`.
Требуется исходная схема всех 35 физических полей. Контракт `temporal_field_contract.csv`
содержит тип, политику использования, ограничение доказательств доступности и число
null / точных пустых строк. Списки не сравниваются с пустой строкой.

Сценарии полноты условны относительно финальной выборки A и предположения о
доступности C40 / предполагаемого аэропорта. `raw_typecode` требует typecode;
`raw_aircraft_class` дополнительно icaoaircrafttype; `raw_metadata_bundle` дополнительно
market_segment и AC_CLASS. Поля восстановления и будущего исхода в них не входят.
Отсутствие времени получения сообщений не позволяет трактовать эти проценты
как доказанное эксплуатационное покрытие.

`temporal_lead_quantiles.csv` и `temporal_horizon_coverage.csv` используют минимум
attempt_times только для ретроспективной диагностики интервала после C40.
Этот будущий timestamp не является предиктором. `temporal_group_coverage.csv`
разбивает каждый сценарий отдельно по аэропорту и месяцу посадки UTC.

## Публичное распространение

Седьмой ноутбук требует локальную split-разметку шестого ноутбука; оба SHA256
проверяются до и после расчета. `preparation_train_vocabulary.json` — точные
строки train без изменения регистра / пробелов; missing_id=-1, unseen_id=-2,
видимые категории имеют номинальные индексы >=0. Индекс не является порядком
или числовым признаком. Будущий one-hot должен явно сохранять состояния
missing / unseen. `preparation_numeric_scaler.json` содержит mean / scale
lat / lon только train (дисперсия с делением на N). `preparation_numeric_audit.csv`
содержит физические диапазоны и диагностические границы, не правила очистки.
UTC-преобразования фиксированы, данные не перезаписаны. `preparation_plan.json`
задает уточненные наборы, сетку регуляризации, метрики и еще не выполненный
bootstrap. Препроцессор проверен частично; классификатор не обучался.

Шестой ноутбук читает финальный parquet и сохраняет кандидатную разметку в
игнорируемом `data/06_candidate_split_labels.parquet`: source_row — порядковый
номер строки с нуля, split — календарная часть либо диагностическое исключение.
Разметка привязана к SHA256 и порядку строк входа, не изменяет базу A.
Публичный `protocol_manifest.json` содержит контрольные суммы и границы UTC.
Временная ось — C40_CROSS_TIME; будущие landing_time / последний attempt
используются только для purge исходов на границе, не входят в признаки.
Порог embargo 24 часа — кандидатное исследовательское решение, не доказанная
достаточность независимости. Время получения меток в таблице отсутствует.

`protocol_key_audit.csv` проверяет точные ключи и число ключей, встречающихся
в нескольких рабочих частях; прокси события не является доказанным физическим
идентификатором. Пересечение самолетов опубликовано отдельно и допускается в
сценарии будущих событий знакомого парка. Ни flight_id, ни icao24 не предикторы.
Составной ключ проверяется на всех записях. Непройденная структурная проверка
фиксируется в манифесте и требует исследования до обучения, а не удаления
повторов без решения. Сценарии без обязательного market_segment сохраняют
пропуски; обработка missing / unseen должна обучаться только на train.

Пятый ноутбук требует исходный и финальный parquet из манифеста A. Для отдельного
репозитория предусмотрены файлы с исходными именами в `data/`.
`metadata_monthly.csv` содержит отдельные counts пропусков и GoA с пропуском для
каждого поля; знаменатель — rows своего этапа и месяца. `metadata_patterns.csv`
кодирует пересечения битами typecode=1, icaoaircrafttype=2, market_segment=4,
AC_CLASS=8. `metadata_exclusive_reasons.csv` задает первое непройденное требование
в том же порядке. `metadata_value_counts.csv` сохраняет сырые строковые категории
без очистки; `<NULL>` / `<EMPTY>` — обозначения физических пропусков для экспорта.
`metadata_boundaries.csv` содержит даты посадки записей с непустыми полями, а не
время появления информации в источнике. Агрегаты не подтверждают корректность
кодов или причину изменения покрытия.

Для отдельного проекта нужно документировать происхождение и лицензию исходного набора, доступ к промежуточным файлам и способ их воспроизведения. Эти условия здесь не предполагаются автоматически. Текущий контракт позволяет запуск на подготовленных артефактах; он не является автономным загрузчиком и всей цепочкой подготовки с нуля.
